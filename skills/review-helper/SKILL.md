# review-helper エージェント手順書

対象: Claude Code / Codex などのコーディングエージェント。
このファイルは「解説つきレビュー画面」を生成するときの共通手順です。
CLI本体（review-helper.ts）と画面テンプレートは、**このSKILL.mdと同じディレクトリ**にあります。
以下のコマンド例の `<スキルのディレクトリ>` は、このファイルがある場所に読み替えてください。

## 前提

- 差分の本文・統計はCLIが機械的に抽出します。**エージェントがdiff本文を書き写すことは禁止**です（捏造・省略の防止）。
- エージェントが書くのは注釈（グループ分け・意図・注意点・指摘）だけです。

## 手順

0. レビュー対象を確定する。

   - ローカルソースのPathが指定された場合は、そのGitリポジトリを作業ディレクトリにして実行する。
   - Pathが省略された場合は、現在の作業ディレクトリにあるGitリポジトリを対象にする。
   - PR URLまたはPR番号が指定された場合は、その値を `extract --pr` に渡す。
     CLIの実行自体はローカルGitリポジトリ内で行う必要がある。
   - 対象が複数考えられる場合だけ、実行前にユーザーへ確認する。

1. 差分を抽出する。

   ```sh
   bun <スキルのディレクトリ>/review-helper.ts extract
   # 範囲を指定する場合: extract main...feature や extract HEAD~3 など
   # 既存PRをレビューする場合: extract --pr <PRのURLまたは番号>（gh CLIで取得。checkout不要）
   ```

2. 標準出力に表示された `diff.json` を読む。各hunkに `h001` のようなIDが付いている。
   レビュー対象は、ローカル差分なら `repoRoot`、PRなら `prRef` で確認する。
   これらはレビュー画面にも自動表示されるため、`annotations.json` に転記しない。

3. 背景情報（`context` 用）を収集する。

   - PRレビュー（--pr指定）の場合、対象PRは `diff.json` の `prRef` に記録されている。
     背景収集は**必ずその値を引数に**して読む（例: `gh pr view <prRefの値> --json title,body,comments`）。
     引数なしの `gh pr view`（現在ブランチのPR）は**別のPRを混入させる危険があるため使わない**。
   - ローカル差分の場合は、現在ブランチにPRがあれば本文とコメントを取得する。
   - PR本文・依頼文に含まれる GitHub Issue / DocBase / Backlog のリンクを洗い出し、
     利用可能な手段（`gh` CLI・各サービスのMCPツール等）で本文を読む。
   - PRが無いローカル差分では、依頼時の会話や plans/ 配下の計画ファイルなど、手元の実在情報のみを使う。
   - **取得できなかった情報は創作しない**。何も無ければ `context` ごと省略する。

4. `diff.json` と同じディレクトリ
   （`$XDG_DATA_HOME/review-helper/<review-id>/`、未設定時は `~/.local/share/review-helper/<review-id>/`）
   に `annotations.json` を書く。
   `review-id` は、PRなら `ORG-REPO-PR番号`、ローカル差分なら
   `ORG-REPO-ローカルPathのhash`（remote不明時は `--hash`）。正確な保存先は
   `extract` の標準出力に表示された `diff.json` のPathを使う。

5. 検証と画面生成を実行する。

   ```sh
   bun <スキルのディレクトリ>/review-helper.ts render
   ```

   検証エラー（未割り当てhunk・重複・不正ID）が出たら、メッセージのIDに従って
   `annotations.json` を修正し再実行する。成功するとブラウザが開く。

6. （推奨）指摘の受け渡しまで自動化する場合は、送信待ちサーバを起動する。
   この流れを使うときは、手順5を `render --no-open` にしてブラウザの二重表示を避ける。

   ```sh
   bun <スキルのディレクトリ>/review-helper.ts serve --once
   ```

   ブラウザが開き、人間が背景・コンテキスト（レビュー全体）やhunk・行に質問・指摘を書いて
   「質問/指摘を送信」を押すと、
   このコマンドがプロンプトを標準出力に出して終了する。**質問には回答し、指摘には対応する**。
   内容は `$XDG_DATA_HOME/review-helper/<review-id>/comments.json`
   （未設定時は `~/.local/share/review-helper/<review-id>/comments.json`）にも保存される。
   （serveを使わない場合、人間は「質問/指摘をコピー」でプロンプトを貼り付けてくる）

   **待機の注意（重要）**: 送信を受け取る前に自分のターンを終えてはいけない。
   - 基本は `serve --once` を**フォアグラウンドで実行時間制限を最大にして**実行し、終了（＝受信）まで待つ。
   - 実行時間制限で待ちきれない環境では、serveをバックグラウンド起動した上で、
     `comments.json` の出現（またはserveログの「指摘を受信しました」）を**ポーリングで待ち続け**、
     受信内容に応答してから終了する。
   - 「送信されたら対応します」と言って待たずに終了するのは禁止。特にヘッドレス実行では
     ターン終了＝プロセス終了であり、バックグラウンドのserveごと消えて受信不能になる。
   - どうしても待機を継続できない場合は、その旨を明示し、人間に `serve` の起動と
     「受信箱パスをコピー」でのプル型連携を案内してフォールバックする。

7. ユーザーに `review.html` のパスと、レビューの見どころ（要注意グループ）を短く伝える。

## annotations.json スキーマ

```json
{
  "title": "レビュータイトル（〜の差分レビュー など）",
  "summary": "変更全体のサマリ1〜2文",
  "context": {
    "background": "PRの背景・解決する問題の説明（任意）",
    "requestedBy": "誰からの要望か（任意）",
    "terms": [{ "term": "初見の人が知らない用語", "desc": "短い説明" }],
    "links": [{ "label": "GitHub Issue #123", "url": "https://example.com/issues/123" }]
  },
  "groups": [
    {
      "title": "グループ名（例: URL・ホスト判定の共通基盤）",
      "summary": "一覧に表示する1行説明",
      "kind": "refactor",
      "risk": "high",
      "intent": "何を・なぜ変えたのかを説明する段落。レビュアーが差分を読む前に読む文章。",
      "notes": ["挙動変更や互換性など、確認時の注意点"],
      "hunks": ["h001", "h003"],
      "findings": [
        { "hunk": "h003", "note": "マージ前に人間の確認・判断が必要な具体的指摘" }
      ]
    }
  ]
}
```

- `kind`: `feature | fix | refactor | test | docs | config | chore | other`
- `risk`: `low`（低リスク） | `medium`（注意） | `high`（要注意）
- `hunks`: **全hunkをちょうど1つのグループに割り当てる**こと。render が機械検証する。
- `summary` / `notes` / `findings` は任意。

## 注釈の書き方

- グループは「意図」単位で3〜9個。ファイル単位ではなく「何をするための変更か」で分ける。
- 並び順は表示順になる。**リスクが高い・レビューの重要度が高いものを先頭に**。
- `context` には、PR説明・Issue・チケット・依頼時の会話など**実在する情報だけ**を書く。
  背景・解決する問題・要望元・関連リンク（GitHub Issue / DocBase / Backlog 等）・初見の人向け用語メモ。
  **URLを推測で創作しない**。情報がなければ context ごと省略する。
- `intent` は「何を・なぜ」。差分を読む前提知識をレビュアーに与える文章にする。
- `findings` は「マージ前に人間が確認・修正すべき具体的な点」だけ。軽微な好みは書かない。
- `collapsed: true` が付いたhunk（ロックファイル・巨大hunk）は精読せず、
  「機械的変更」などの低リスクグループにまとめてよい。
- すべて日本語で書く。対象領域に詳しくないジュニアエンジニアにも伝わる表現にする。
